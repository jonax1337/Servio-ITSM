# Module & feature map

This is the internal working reference for anyone (human or Claude Code) extending Servio. It maps every feature to its real files so you can jump straight to the right place. Every path below was verified against the code.

Servio has two surfaces:

| Surface | Route root | Audience | Layout |
| --- | --- | --- | --- |
| **Agent console** | `app/(console)/*` | Agents, managers, admins | `app/(console)/layout.tsx` (sidebar + topbar) |
| **Self-service portal** | `app/portal/*` | End users (requesters) | `app/portal/layout.tsx` (portal nav) |

Auth pages live at `app/login` (not a route group). There is **no `src/` directory** — everything is at the repo root. The request middleware is `proxy.ts` (Next 16 naming), not `middleware.ts`. See [architecture.md](./architecture.md) for the request lifecycle and auth/role gating.

## Per-module anatomy

Shared identity lives in `components/brand.tsx` (Relay and outlined wordmarks),
`components/sable-mark.tsx` (Nova Flow), `app/globals.css` (interface tokens) and
`app/layout.tsx` (fonts and metadata). Application copies are generated by
`scripts/sync-brand-assets.mjs`; see [branding.md](./branding.md).

Console modules follow one consistent shape. When adding a feature, mirror this layout so agents and contributors can predict where things live:

| Concern | Location | Notes |
| --- | --- | --- |
| List page | `app/(console)/<mod>/page.tsx` | Server Component; queries `lib/db`, renders table/cards. `export const dynamic = "force-dynamic"`. Filters + pagination are URL-driven; tables sort via `<SortableHead>` (`?sort=&dir=`, mapped to a Prisma `orderBy`). |
| Detail page | `app/(console)/<mod>/[id]/page.tsx` | Loads one record + related data; renders a `*-properties` panel and action components. |
| Create page | `app/(console)/<mod>/new/page.tsx` | Renders the `*-form` component. Some modules create via a dialog instead (e.g. Locations, Categories). |
| Server actions | `lib/actions/<mod>.ts` | All mutations. `"use server"`, Zod-validated, role-checked via `lib/session`, then `revalidatePath`. |
| UI components | `components/<mod>/` | Client components: forms, dialogs, property panels, action buttons. |
| Select options | `lib/data/options.ts` | Single cached `getFormOptions()` supplies dropdown data (users, groups, categories, services, etc.) to every form. |

Enums, status/priority metadata, and reference helpers (`ticketRef`, `problemRef`, `changeRef`, `PRIORITY_META`, `TICKET_STATUS_META`, `OPEN_TICKET_STATUSES`) live in `lib/constants.ts` — **not** `lib/enums.ts`. Navigation grouping and per-item role gating live in `lib/nav.ts` (`consoleNav`, `filterNav`). See [data-model.md](./data-model.md) for the underlying Prisma models. To contribute a new module, follow the pattern below and read [../CONTRIBUTING.md](../CONTRIBUTING.md).

## Navigation groups

`lib/nav.ts` groups console modules and gates each by `minRole` (`AGENT` < `MANAGER` < `ADMIN`; `filterNav` hides items above the user's rank):

| Group | Modules |

## Overview

### Sable (AI assistant)
Servio's built-in AI service-desk agent — a chat surface that can read the queue,
search the app and the web, and **propose changes the user approves before anything is written**.
The display name is **Sable** (`AI_ASSISTANT_NAME` in `lib/constants.ts`); code identifiers and
filenames match it (`sable-*`/`Sable*`). Full write-up: [ai.md](./ai.md).

mutation.

## Service Operations

### Tickets
The core incident/request module and the richest one in the codebase.

| | |
| --- | --- |
| Routes | `app/(console)/tickets/page.tsx`, `[id]/page.tsx`, `new/page.tsx` |
| Actions | `lib/actions/tickets.ts` |
| Components | `components/tickets/` |

Actions include `createTicket`, `updateTicketField` (incl. switching `type` — the ref prefix stays fixed), `updateTicketDetails`, `addTicketComment`, `escalateTicket`, `toggleMajorIncident`, `toggleWatch`, `addParticipant`, `linkTicket`/`unlinkTicket`, `setTicketParent` (parent / child tickets: cycle, depth and finished-parent rules in `lib/ticket-hierarchy-rules.ts`, UI in `components/tickets/ticket-hierarchy.tsx`; `setTicketResolution` with `resolveChildren` resolves a parent's open direct children through the same code path and reports refused ones), `mergeTicket`/`unmergeTicket` (rules in `lib/merge-rules.ts`: a merge carries comments, watchers, assets, attachments, links, problem/change and child tickets to the target and records them in `TicketMerge`; the merged ticket's banner offers "Undo merge"; a merged ticket can't be reopened by status change), cross-entity linking (`setTicketProblem`, `setTicketChange`, `linkAsset`/`unlinkAsset`, `unlinkRelation`; the ticket page lists links in both directions, labelled from the viewing side — "Blocks" vs "Blocked by" — via `lib/ticket-link-labels.ts`), `setTicketResolution`, `setTicketPending`, `setTicketDueDate`, **problem and article from a ticket** (an incident's Actions menu and Links tab offer *Create problem from this incident* — `components/tickets/raise-problem-dialog.tsx`, prefilled by `problemDraftFromTickets` in `lib/ticket-drafts.ts`, with the similar incidents as checkboxes and the problem's required custom fields, which `listRaiseProblemFields` returns for the traits the problem inherits; `createProblemFromTickets` reports and audits the tickets it really linked and rolls the problem back when every ticket was taken meanwhile; a resolved or closed ticket offers *Create knowledge article*, which opens `/knowledge/new?fromTicket=<id>` prefilled by `articleDraftFromTicket` in `lib/article-drafts.ts` and links the saved article to the ticket; for a ticket the agent cannot act on the editor stays empty and an inline note says so), `forwardTicketExternal`, and work-log entries (`addWorkLog`, `deleteWorkLog`). Key components: `ticket-form`, `ticket-properties` (every property saves the moment it is changed: optimistic update, a toast with **Undo** for 6 s (`UNDO_WINDOW_MS` in `lib/ticket-property-edits.ts`), rollback plus an error toast when the action refuses; Undo is a compare-and-set, so it never overwrites a newer change: each undo write carries the value the field held right after the edit (`expected`, built by `undoChanges`) and `updateTicketField` applies it only while the field still has that value, otherwise it refuses with "This field changed since — not undone", and the toast withdraws Undo as soon as the field no longer matches or the workflow forbids the way back (`undoBlocker`); undoing an assignment is a real change, not a silent rollback: the previous assignee is notified again; each edit still goes through `updateTicketField`, so authz, audit, SLA and automations are unchanged; the Resolve / Pending dialogs commit on **Confirm** via `setTicketResolution` / `setTicketPending`, with Enter or Ctrl/Cmd+Enter confirming — `lib/confirm-shortcut.ts`), `ticket-actions`, `work-log`, `resolution-dialog`, `pending-reason-dialog`, `due-date-picker`, `sla-badge`, `form-answers`, `macro-picker` (apply a canned macro in one click), plus the reusable `link-picker` (attach problems/changes/assets), `saved-views-bar`, and `ticket-tasks` (sidebar checklist — actions `addTask`/`toggleTask`/`deleteTask`). Create forms (`ticket-form`, `problem-form`, `change-form`) include admin-defined custom fields (`components/custom-fields/form-custom-fields`).

**Cross-field search & CSV export:** the tickets list uses `lib/search.ts` (`ticketSearchWhere`/`applyTicketSearch`) for a free-text `q` that spans title, description, comment bodies, requester name/email, and custom-field values (plus a bare-number match on the ticket id) — SQLite-portable, ANDed onto the existing filters. The same helper backs the global `/api/search` route. An **Export CSV** button on the list (and dashboard) hits `GET /api/export?type=tickets` (AGENT+), built on the shared `lib/csv.ts` (`toCsv`/`csvResponse`).

**Saved views:** `/tickets` carries a searchable list of saved filter sets (`SavedView`) — apply/save/delete named filters, personal or (MANAGER+) shared with a team. Actions in `lib/actions/saved-views.ts`; `SAVED_VIEW_KEYS` in `lib/saved-view-filters.ts` is the single list of filter params a saved view may carry (the `/tickets` bar and `createSavedView` both use it, so a view keeps its `sla` filter).

**SLA column:** the tickets table has an **SLA** column (hidden below `md`) built from the same live `slaSnapshot` clock as the ticket's SLA badge (`activeSlaClocks` in `lib/sla-views.ts`, cell text in `lib/sla-column.ts`): *Breached* with "overdue 3h", *At risk* / *On track* with the time left, *Paused*, and an empty cell for a ticket without a deadline or a finished one. The column header sorts by urgency (`?sort=sla`, `sortBySlaUrgency` in `lib/sla-views.ts`): breached first (longest overdue first), then at risk, on track and paused by nearest deadline, tickets without a clock last. The **SLA** filter in the list toolbar (*Breached, At risk, On track, Paused, No active SLA*) sets `?sla=breached|at_risk|on_track|paused|none` — the same param the dashboard's clickable *SLA breached* / *SLA at risk* tiles deep-link to (`slaViewHref`), the CSV export and saved views carry. *No active SLA* is a plain SQL filter (finished tickets and tickets without a deadline, exactly the empty cells); the other values are resolved to ticket ids by `loadTicketListQuery`. Classification is cut down by a SQL prefilter first (`slaViewCandidateWhere`: wall-clock tickets whose deadline has passed for *breached*, or is still ahead for *at risk* and *on track*; tickets on a business calendar always pass because their clock counts working time), then the survivors are classified on the live clock. The ids are not cached, so the filter always agrees with the SLA column of the same page (the dashboard tiles stay cached by the dashboard itself, 60 s), and they go into one `id IN (…)` list, which SQLite (3.32 and later) and Postgres accept up to 32 766 and 65 535 variables per statement.

**Automatic closing:** with Settings › Tickets › *Close resolved tickets automatically after (days)* above 0 (`TICKET_AUTO_CLOSE_DAYS`, default 0 = off), `lib/ticks/auto-close.ts` (`runAutoCloseTick`, hourly by default) moves every ticket that has been RESOLVED that long to CLOSED (`closedAt` set), claimed with a conditional write so a reopen in between wins. It writes an internal note and an audit entry by the Automation account and runs the `TICKET_UPDATED` automations; nothing is closed while the status workflow forbids RESOLVED → CLOSED. A requester reply before the deadline reopens the ticket as before (a plain thank-you does not, and the countdown keeps running); resolving it again starts a new countdown. The "Ticket resolved" email carries `{{autoCloseDays}}` and the localized sentence `{{autoCloseNotice}}` (both empty while off). Rules in `lib/auto-close-rules.ts`.

**Refusals & list order:** ticket actions (`updateTicketField`, `setTicketResolution`, `setTicketPending`) return `{ ok, error }` and report why a change was refused (e.g. not a member of the ticket's group, awaiting approval, workflow disallows it) instead of silently doing nothing. On the ticket list, priority sorts by severity and status by lifecycle order, not alphabetically (`lib/ticket-list.ts` `sortByRank`).

**Bulk actions & sorting:** the tickets table (`components/tickets/tickets-table.tsx`) has row checkboxes + a bulk bar whose **Edit fields…** dialog (`components/tickets/bulk-edit-dialog.tsx`) sets status, priority, group, assignee and category together and applies them once, ending in a "5 tickets updated" toast, or "3 tickets updated, 2 skipped" with the first reasons (grouped by reason, e.g. "This request is awaiting approval… (T-4, T-9)"). A refused request (nothing applied, or a network failure) keeps the dialog open and shows the message inline and as a toast. `bulkUpdateTickets` takes the ids plus a JSON `patch` (validated and ordered by `lib/bulk-edit.ts` — group before assignee, no statuses that need a reason) and re-runs `updateTicketField` per ticket and field, so authorization, transitions, SLA, audit and automations stay correct. Before anything is written every ticket is checked against the whole patch (`planBulkTicket` in `lib/bulk-edit.ts`: access in the current and, for later fields, the new group, assignee membership in the target group, approval and merge state, workflow transition) and a ticket that would refuse any field is skipped with its reason. Automations can still re-route a ticket between two field writes; if that makes a later field refuse, the ticket is reported as *partially updated* ("3 tickets updated, 1 partially updated, 2 skipped") with the refusal in the toast detail, apart from the skipped ones, which were not changed at all. The bar also has a **Create problem** action that raises one problem linked to every selected ticket (`createProblemFromTickets`). All list tables (tickets, problems, changes, assets, people, groups) have sortable columns via `components/sort-header.tsx`.

### Changes
Includes a built-in approval workflow.

| | |
| --- | --- |
| Routes | `app/(console)/changes/page.tsx`, `[id]/page.tsx`, `new/page.tsx` |
| Actions | `lib/actions/changes.ts` — `createChange`, `updateChangeField`, `updateChangeDetails`, `addChangeComment`, `updateChangeWindow`, `updateChangeText`, `setChangeProblem`, `submitChangeForApproval`, `addChangeApprover`, `removeChangeApprover`, `decideApproval`, `setCabRule` (CAB quorum/percent rule); `lib/actions/change-assets.ts` — `attachAffectedCi`/`detachAffectedCi`. Under a REST API actor `createChange` returns `{ createdId }` instead of redirecting. REST: `app/api/v1/changes/` (runs these actions as the token owner) |
| Components | `components/changes/` — `change-form`, `change-properties`, `approval-panel`, `approval-actions`, `add-approver`, `remove-approver`, `submit-for-approval`, `change-window-editor`, `change-editors`, `change-problem-link`, `closure-dialog`, `cancel-change`; affected-CI panel with automated impact/risk |

**Change rules** (`lib/change-rules.ts`): the planned end must be after the start; submitting for CAB requires an implementation plan, a rollback plan and a planned window (a pre-approved standard change is exempt) and reports what is missing; `STANDARD` can only be reached through an active `STANDARD` template (free form, `updateChangeField` and Sable refuse it), and editing the plans, risk or impact of a templated standard change turns it into `NORMAL` (back to `DRAFT` with a comment if it was already pre-approved); the window (`updateChangeWindow`, `change-window-editor`) is editable only in `DRAFT`/`REJECTED`, i.e. before approval. A `DRAFT` change has no manual status moves except `CANCELLED`; it leaves draft through the dedicated submit action (`submitChangeForApproval`: `DRAFT` → `APPROVAL`, or straight to `APPROVED` when no board is needed) — there is no `SUBMITTED` status. The change and problem lists search by ref (`lib/ref-search.ts`: `CHG-0025`, `#25`, `25`) as well as title.

**Lifecycle (`lib/change-rules.ts`):** in `APPROVED`/`SCHEDULED` the window can still move, but only with a reason, which is posted as a comment (`rescheduleError`/`rescheduleComment`) — the dates cannot be cleared. `APPROVAL`/`APPROVED` are set by the approval workflow, never by a manual status edit (`manualStatusError`). Moving to `CLOSED` or `FAILED` needs an `outcome` (`CHANGE_OUTCOMES`; `FAILED` accepts only Failed / Rolled back) and `closureNotes` (post-implementation review; the message is stricter for `EMERGENCY`), collected in `closure-dialog` (`closureError`). `CANCELLED` needs a `cancelReason` (`cancel-change`) and settles the approval board: unanswered seats become `CANCELLED` (`settlesApprovalBoard`). `actualEnd` is stamped when work stops (`REVIEW`/`FAILED`/`CLOSED`). `CLOSED` and `CANCELLED` changes are locked (`isChangeLocked`): everything is read-only except comments and links. A change links to at most one problem via `setChangeProblem` (also reachable from the problem's "Fix changes" card).

**Creating a change:** the *New change* form (`components/changes/change-form.tsx`) includes an **Affected CIs** multi-select (`components/multi-combobox.tsx`, search-as-you-type through `searchAffectedCis`: up to 20 in-service assets matching name, tag or serial per search, `lib/affected-ci-search.ts`; chosen assets show as removable chips, Backspace removes the last); `createChange` and `createChangeFromTemplate` attach them as `ChangeAsset` rows in the same write, so the Impact tab already shows them. While a draft cannot be submitted, the Submit control names each missing prerequisite (`submitBlockerDetails` in `lib/change-rules.ts`) and links it to its field on the Planning tab (`?tab=planning#implementation-plan`, `#rollback-plan`, `#planned-window`).

**CAB quorum & affected CIs:** a change carries an `approvalRule` (`UNANIMOUS` / `QUORUM` / `PERCENT`) + `approvalThreshold`; `lib/cab.ts` (`evaluateCab`) tallies seated approvals against the rule and reports whether the board is satisfied, and `setCabRule` (MANAGER+) can lower the bar mid-flight. The affected-CI panel attaches `ChangeAsset` rows and surfaces blast-radius impact from `lib/cmdb-graph.ts` (`computeImpact`).

### Approvals
A cross-cutting inbox for the current user's pending approvals (currently backed by change approvals).

| | |
| --- | --- |
| Route | `app/(console)/approvals/page.tsx` (list only — no detail/new) |
| Actions | `lib/actions/approvals.ts` — `decideApproval` (advances multi-stage catalog approvals), `seatCatalogStage`/`seatCatalogApprovalStages` (seat the ordered stages), plus the generic ad-hoc `requestApproval`/`decideEntityApproval`/`cancelApproval` |
| Components | `components/approvals/approval-decision` |

**Inbox tabs & four-eyes:** the inbox is split into *All / Changes (CAB) / Service requests / Other* tabs with counts (`?tab=`, built on `EntityTabs`; `approvalTabs`/`tabShowsSection` in `lib/approval-rules.ts`), each card keeping inline Approve/Reject. By default the requester and the owner of a change can never approve it, not even as ADMIN (`changeSelfApprovalError` in `lib/approval-rules.ts`): the inbox and the change's CAB tab replace the decision controls with the rule's explanation, and `decideApproval` in `lib/actions/changes.ts` returns the same message, which `ApprovalActions` shows inline and as a toast.

**Self-approval for small teams:** a team of one cannot satisfy a four-eyes rule, so an admin can relax it under Settings › Change management (`/settings/changes`, setting `CHANGE_SELF_APPROVAL`, read by `getChangeSelfApprovalMode` in `lib/settings.ts`):

| Mode | Seating at submit (`seatBoard` in `lib/change-rules.ts`) | Deciding (`decideApproval`) |
| --- | --- | --- |
| `OFF` (default) | Owner and requester are never seated; an empty board blocks the submit | Owner and requester are refused, as above |
| `WHEN_NO_OTHER_APPROVER` | Owner and requester are seated only when the board would otherwise be empty | Their seat counts like any other under the board's rule |
| `ALWAYS` | Owner and requester are seated next to the auto-selected board, ahead of it on an emergency board (manual seats stay first) | Their own decision settles the board on its own, whatever the rule; the other pending seats are withdrawn |

In every mode the role still has to fit the risk (`approverRolesForRisk`: a high-risk change needs an ADMIN, so a MANAGER account never self-approves one; `SELF_APPROVAL_ROLE_ERROR`), a self-approval is only ever on one's own seat (the admin override never decides another approver's seat on one's own change), and it needs a written justification (`selfApprovalCommentError`). The audit entry reads `Self-approval: approved CHG-… as its requester/owner` and carries `meta.selfApproval`, the mode and the justification; the submit entry notes when the requester/owner was seated. `ApprovalActions` (prop `selfApproval: { settlesBoard }`) shows the controls with a self-approval note, a required justification field and disabled buttons until it is filled; `ApprovalPanel` marks the requester's and owner's seats with a *Self-approval* badge. The UI text lives in `messages/{en,de}/changes.ts` (`approvalActions.selfApprovalHint*`, `approvalActions.justificationPlaceholder`, `approvalPanel.selfApprovalBadge`) and `messages/{en,de}/settings.ts` (`changes.*`, the settings card); the new refusals are translated in `messages/server/de/changes.ts` and `admin.ts`. Audit summaries stay English, like all stored text. Seats are checked when the change is submitted: an owner or requester seated in an earlier round is dropped and re-seated by the current mode, and a seat left from a mode that has since been switched off cannot be decided (a manager can remove it).

**Catalog requests and sign-offs:** `decideApproval` (catalog stages) and `decideEntityApproval` (ad-hoc sign-offs) return an `ActionResult` instead of silently returning. `decisionRefusal` in `lib/approval-rules.ts` decides who may act: only a pending approval, only its assigned approver (or an admin), and never the person who raised the request. The check is requester-based: it compares the approver with the request's requester, not with the ticket's assignee or owner. The inbox and the entity approval cards replace the controls with that explanation for the requester, and `ApprovalDecision`, `EntityApprovalDecision` and the entity cards show a refusal inline and as a toast and never a success toast.

**Multi-stage / group catalog approvals:** a `CatalogItem` can define ordered `approvalStages` (each an approver *or* a group) via `lib/actions/catalog-admin.ts` → `updateApprovalStages` (editor UI in the catalog admin page). New requests seat stage 0; approving a stage advances to the next (`seatCatalogStage`), and a rejected/cancelled request can be re-raised with the saved answers via `lib/actions/catalog.ts` → `reRequestCatalogItem`. The portal shows a stage-progress timeline, including each approver's decision comment to the requester.

**Awaiting approval = cancel only:** while `approvalState` is `PENDING` (or already `CANCELLED`) the only allowed status change is `CANCELLED` (`approvalAllowsStatus` in `lib/transitions.ts`) — enforced in console actions, macros, automations, the REST API (`409`) and Sable. Cancelling sets `approvalState` to `CANCELLED` and withdraws the pending approvals (`withdrawPendingApprovals` in `lib/approval-seating.ts`).

### Recurring tickets

Tickets created on a schedule — GLPI's "recurrent items" — for routine work such as certificate renewals, license reviews and backup restore tests.

| | |
| --- | --- |
| Route | `app/(console)/settings/recurring-tickets/page.tsx` (MANAGER+, via the `/settings` prefix; card on the Settings hub) |
| Actions | `lib/actions/recurring-tickets.ts` — `createRecurringTicket`, `updateRecurringTicket`, `setRecurringTicketActive` (pause / resume), `deleteRecurringTicket`, `runRecurringTicketNow` ("Create now"); all MANAGER+ (`requireManagerUser`) |
| Rules / data | `lib/recurring-ticket-rules.ts` (pure recurrence math: `occurrenceAt`, `creationTimeFor`, `initialNextDue`, `nextToCreate`, `leadTimeError`), `lib/recurring-ticket-input.ts` (Zod for the form and the REST bodies, API → form translation), `lib/recurring-tickets.ts` (`fireRecurringTicket`: claim + `createTicketCore`) |
| Components | `components/recurring-tickets/recurring-ticket-manager.tsx` (list, create/edit dialog with a preview of the next occurrences, pause switch, "Create now", delete) |
| Tick | `lib/ticks/recurring-tickets.ts` — `runRecurringTicketsTick` (every `RECURRING_TICKETS_TICK_SECONDS`, default 300 s; gated by `RECURRING_TICKETS_ENABLED`) |
| REST | `GET/POST /api/v1/recurring-tickets`, `GET/PATCH/DELETE /api/v1/recurring-tickets/{id}` (see [rest-api.md](./rest-api.md#recurring-tickets)) |

A schedule is a ticket template (title, description, type, priority, impact, urgency, requester, assignee, group, category, service) plus a recurrence: `DAILY` / `WEEKLY` / `MONTHLY` / `YEARLY` every `interval` units from `firstDueAt`, on the same wall-clock time in its `timezone`. Monthly dates past a month's end clamp to the last day without drifting (Jan 31 → Feb 28/29 → Mar 31). The ticket of an occurrence is created `createBeforeDays` local days before it is due; the lead time must be shorter than one step, so at most one upcoming occurrence is open at a time. No requester means the schedule's creator.

- **Exactly once.** The tick (and "Create now") claims an occurrence by moving `nextDueAt` with a conditional update on the value it read, then creates the ticket through `createTicketCore` — SLA, VIP repricing, requester/assignee mail, `TICKET_CREATED` automations and auto-assign — with `source = RECURRING`, the occurrence's due time as `dueDate`, and the Automation user as the actor (the manager for "Create now"). A second tick, a restart or a concurrent edit finds the marker moved and creates nothing. A creation that fails after the claim is not retried by itself: `lastError` is shown in the list, the creator gets a `RECURRING_TICKET_FAILED` notification, and "Create now" re-runs it.
- **Catch-up once, no flood.** After a downtime only the latest missed occurrence is created, then the one whose window is open now, if any; older missed occurrences are skipped (the audit row counts them).
- **Pause / edit.** Paused schedules create nothing. Resuming, or changing the recurrence, recomputes `nextDueAt` as the first occurrence that is not due yet (and after `lastCreatedFor`), so occurrences that fell due meanwhile are not created retroactively. Editing only the template keeps `nextDueAt`.
- **Create now** creates the next occurrence that is not due yet right away (also for a paused schedule); the schedule then moves on to the one after it.
- **Audit.** `CREATE` / `UPDATE` / `DELETE` rows on entity `RecurringTicket`; each generated ticket writes an `AUTOMATION` row on the schedule (with the ticket id, due time, trigger `SCHEDULE` / `MANUAL` and skipped occurrences) next to the ticket's own `CREATE` row.
- Template fields are the ticket's built-in fields only; required custom fields make the creation fail (shown as `lastError`).

**Business-hours SLA & escalation:** when an `SLA` references a `BusinessCalendar`, deadlines are computed in working time (`lib/business-hours.ts` `elapsedBusinessMs`/`addBusinessMs`, wired through `lib/sla.ts`; wall-clock when no calendar is set). `lib/sla-escalation.ts` (`runSlaEscalation`, swept by the scheduler) fires each `EscalationStep` (`NOTIFY`/`REASSIGN`/`BUMP_PRIORITY`) at its `thresholdPercent`, durably at-most-once, and handles first-response breach. `BUMP_PRIORITY` deliberately does **not** reprice the SLA (a tighter tier measured from creation would breach at once).

**Re-pricing:** a priority/service/SLA change re-measures the deadlines from the ticket's creation plus the pause time it already banked — the clock never restarts, so raising a priority can make a ticket late at once. A priority-bound SLA follows the new priority unless that SLA was picked explicitly; a recorded first response keeps its response deadline; terminal tickets are untouched. Every priority writer (console, macros, escalate, major incident, REST, automations, VIP bump) shares `slaRepricePatch` in `lib/sla.ts`. Resolving a ticket nobody answered stamps the first response. The dashboard **SLA met** gauge counts only resolved tickets that ran under an SLA, plus active, unpaused tickets already past their resolve deadline.

### Mail threading & inbound replies
Subject refs use the stored ticket prefix (stable after a type switch). The auto-acknowledgement for a ticket created from an email threads onto the customer's original `Message-ID`. Quoted reply history (Outlook/Gmail/Apple attributions, `>` quotes) is stripped from inbound reply comments by `lib/mail-inbound/reply-strip.ts`; the raw mail stays in the mail log and forwards (`Fwd:`/`WG:`) are left untouched. A requester reply to a ticket parked on "awaiting customer" resumes it (status OPEN, SLA clock running); a short thank-you-only reply leaves a resolved ticket resolved (`lib/thank-you-reply.ts`). Forwards to external parties carry the attachments of the forwarded public messages and the requester-side ticket files (never agent uploads), and customer-facing mail never references the vendor side of the thread. Stripping is conservative (inline answers survive) and bounded: bodies over 200k characters are stored unstripped. A customer reply reopens a resolved ticket (see Portal).

### CSAT surveys
A post-resolution satisfaction survey. On a ticket's resolution, `lib/actions/tickets.ts` mints a `SurveyResponse` row and the resolution email ([`lib/email-templates.ts`](../lib/email-templates.ts)) carries a token link. The resolution mail CCs the ticket's participants, threads onto the ticket's mail conversation, and includes the public resolution note (`{{resolution}}` template variable; omitted for an internal note) and, when resolved tickets close automatically, the delay (`{{autoCloseDays}}`, `{{autoCloseNotice}}`). The rating page is **public and unauthenticated** (the token is the credential) — `proxy.ts` whitelists `/survey`.

Portal write paths are deliberately narrow and share one routed core (`lib/portal-tickets.ts`): requesters (and Sable, acting as them, confirm-first) can only create tickets/catalog requests, reply on their **own** tickets, and stage attachments (images/PDF/`.eml`, re-parented onto the new ticket). Catalog requests pre-route to the item's service/category team; free-form tickets default to the Service Desk triage team. Customer replies (portal, Sable, inbound mail) reopen `RESOLVED`/`CLOSED` tickets through the configured workflow (`reopenOnCustomerReply` in `lib/ticket-core.ts`); portal replies and attachments are refused on `CLOSED`/`CANCELLED` tickets. Replies are rate-limited per user (`REPLY_RATE_LIMIT`, 10/min) and uploads by `USER`-role accounts too (`UPLOAD_RATE_LIMIT`, 30/min) — see [configuration.md](configuration.md). All privileged mutations stay in the console action files.
