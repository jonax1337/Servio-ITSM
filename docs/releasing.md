# CI & releases

How Servio is checked on every change and how a release reaches GitHub and the
container registry. The workflows live in [`.github/workflows/`](../.github/workflows).

---

## ✅ Continuous integration — `ci.yml`

Runs on every pull request, on every push to `main`, and on demand
(`workflow_dispatch`). The jobs run in parallel:

| Job | What it proves |
| --- | --- |
| **Lint, types, schema & unit tests** | `prisma validate`; committed migrations produce exactly `schema.prisma` (`prisma migrate diff … --exit-code`); `brand:check`; `pnpm typecheck` (`next typegen && tsc --noEmit`); `pnpm lint`; `pnpm test` (Vitest). On PRs it also prints the advisory [doc-drift](./maintaining-docs.md) report. |
| **Production build** | `pnpm build` succeeds with throwaway env values and no `.env` file. |
| **Link crawl (Playwright)** | Builds the app against a migrated and seeded throwaway SQLite DB, logs in as each role and crawls every linked page (see [Link integrity tests](#-link-integrity-tests)). On failure the Playwright report is uploaded as an artifact. |
| **Docker image builds** | The [`Dockerfile`](../Dockerfile) and [`updater/Dockerfile`](../updater/Dockerfile) build; the app container refuses a database with migrations it does not ship, then boots (migrations + seed via [`docker/entrypoint.sh`](../docker/entrypoint.sh)) and serves `/login`. |
| **Updater end-to-end** | [`tests/updater-e2e/run.sh`](../tests/updater-e2e/run.sh) runs the real updater and socket proxy against a local registry: an update to a good release succeeds, and a broken release is rolled back with the database restored byte-for-byte. See [updates.md](./updates.md). |

CI uses Node 24 LTS (the base of the production image) and the pnpm version pinned
in `package.json#packageManager`. To reproduce a failing job locally:

```bash
pnpm install --frozen-lockfile
pnpm exec prisma migrate diff --from-migrations prisma/migrations \
  --to-schema-datamodel prisma/schema.prisma \
  --shadow-database-url file:./ci-shadow.db --exit-code
pnpm typecheck && pnpm lint && pnpm test && pnpm build
```

> **Migration drift fails CI.** If you change `prisma/schema.prisma`, commit the
> migration generated by `pnpm db:migrate` in the same PR (see
> [data-model.md](./data-model.md)).

To make the checks mandatory, mark the CI jobs as **required status
checks** in the branch protection rule for `main`.

## 🔗 Link integrity tests

Two layers keep internal links from pointing at routes that do not exist.

| Layer | Where | What it checks |
| --- | --- | --- |
| **Static** | [`tests/unit/route-links.test.ts`](../tests/unit/route-links.test.ts), part of `pnpm test` | Builds the route manifest from `app/**/page.tsx`, `route.ts`, metadata files and `public/`, extracts every internal link target from `app/`, `components/`, `lib/` (JSX `href`/`backHref`, nav and config objects, `redirect`, `router.push`, `revalidatePath`, `new URL("/…")`, entity-to-path maps) and fails with `file:line -> target` when a target matches no route. Also checks that every approval, article-link and inline-ref entity type resolves to a detail page. No DB, no network. |
| **Runtime** | [`e2e/links.spec.ts`](../e2e/links.spec.ts), `pnpm test:e2e` | Logs in through the real `/login` form as ADMIN, MANAGER, AGENT and USER (seed users) and crawls same-origin `a[href]` links breadth-first from `/` (staff) or `/portal` (USER). Pages are only navigated, never clicked or submitted. Visits at most 3 concrete URLs per page shape (id-like segments collapsed, so `/contracts/licenses` is not hidden behind `/contracts/[id]`) and 250 pages per role. |

The crawler reports a page as broken when it answers HTTP 400 or above, renders the
not-found or an error-boundary heading, raises an uncaught page error, or when the
proxy redirects away from it: a link **shown** to a role that ends on `/no-access`,
`/login` or (for the USER role) `/portal` is a bug in what that role is shown. Every
failure is listed in one table (role, source page, target, reason).

Links that are broken today but wait for a decision go into `KNOWN_BROKEN` in the
static test, with a one-line reason; the test fails once such an entry is fixed so the
list cannot go stale.

Run the crawler locally against a production build (port 3200, throwaway DB):

```bash
export DATABASE_URL=file:./e2e.db AUTH_SECRET=e2e-only AUTH_TRUST_HOST=true   APP_URL=http://localhost:3200 AUTH_URL=http://localhost:3200 SCHEDULER_ENABLED=false
pnpm exec prisma migrate deploy && pnpm db:seed
pnpm build
pnpm exec playwright install chromium   # first run only
pnpm test:e2e                           # starts `next start -p 3200`, or reuses a running one
```

Delete `prisma/e2e.db` afterwards. `playwright-report/` and `test-results/` are git-ignored.

## 🚀 Releases — `release.yml`

A release is a version tag. You decide when to cut one:

```bash
git switch main && git pull
pnpm release 0.2.0                 # or 0.2.0-rc.1 for a prerelease
git push --follow-tags origin main
```

[`scripts/release.mjs`](../scripts/release.mjs) refuses unless you are on a clean
`main`, the tag does not exist yet and the version is later than the current one.
It then writes the version into every file that carries it (`package.json`,
`updater/package.json` and `APP_VERSION` in `lib/constants.ts`), commits
`chore(release): v0.2.0` and creates the annotated tag `v0.2.0`. Versions follow
Semantic Versioning 2.0 and are ordered exactly like the updater orders releases
(`updater/versions.mjs`). A unit test
(`tests/unit/app-version.test.ts`) fails when these files disagree.

Pushing the tag starts the workflow:

1. **Verify.** `node scripts/release.mjs --check vX.Y.Z` fails the run when the tag
   and the version files disagree, for example after tagging by hand.
2. **CI.** The full [`ci.yml`](#-continuous-integration--ciyml) runs on the tagged
   commit (as a reusable workflow). Nothing is published unless every job passes.
3. **Images.** The app and the updater sidecar are built natively on `linux/amd64`
   and `linux/arm64` runners and pushed to GHCR, then published as multi-arch tags:

   | Tag | Moves |
   | --- | --- |
   | `ghcr.io/<owner>/servio:X.Y.Z` | never — pin this in production |
   | `ghcr.io/<owner>/servio:X.Y` | to the latest patch of that minor (not for prereleases) |
   | `ghcr.io/<owner>/servio:latest` | to the newest stable release |

   `servio-updater` gets the same tags.
4. **GitHub Release.** Only after both images are published, the workflow creates
   the GitHub Release with GitHub's generated notes (merged PRs and contributors
   since the previous tag) and the `docker pull` commands. A version with a `-`
   suffix becomes a prerelease. The in-app updater ([updates.md](./updates.md))
   offers exactly these GitHub Releases, so it never sees a release whose images
   are missing.

If a run fails, fix the cause and re-run the failed jobs; pushing the same tag
again is not needed, and the release step skips a release that already exists. If
`pnpm release` itself fails (for example a commit hook), it restores the version
files and creates neither commit nor tag. Third-party actions in both
workflows are pinned to commit SHAs with the version as a comment; Dependabot
updates them.

### One-time repository setup

- **GHCR visibility:** the first release creates the `servio` and `servio-updater`
  packages as private. Make them public under *Packages › Package settings* so
  servers can pull without credentials, or log the servers in with a read-only token.

No extra token or workflow permission is needed: the default `GITHUB_TOKEN`
pushes the images and creates the release.

## 🔄 Dependency updates — `dependabot.yml`

[Dependabot](../.github/dependabot.yml) opens weekly PRs for GitHub Actions
(grouped), npm packages (minor and patch grouped; at most 5 open PRs) and the
Docker base image, with `ci:` and `chore:` commit prefixes. Majors of Prisma and
imapflow and Node image majors are ignored on purpose: they need their own
migration branch, and the image follows the Node LTS line by hand. `@types/node`
majors are ignored for the same reason; they move with the next Node LTS bump.
