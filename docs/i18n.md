# Internationalization (i18n)

Servio's console, portal and sign-in pages are translated. English is the source language;
German ships complete. There is no locale prefix in URLs: Servio is an internal tool, so the
**user's setting** decides, not the address.

See also: [architecture.md](./architecture.md) · [configuration.md](./configuration.md) ·
[design-system.md](./design-system.md).

## 🌐 How the locale is chosen

`getLocale()` in [`lib/i18n/server.ts`](../lib/i18n/server.ts) resolves it once per request,
with the precedence in `pickLocale()` ([`lib/i18n/config.ts`](../lib/i18n/config.ts)):

| Situation | Locale |
| --- | --- |
| Signed in, `User.locale` is a supported code (`en`, `de`) | that locale |
| Signed in, `User.locale` is `auto` (the default for new users) | the instance default |
| Signed out (login, survey, maintenance page) | the `servio-locale` cookie, else the instance default |
| Nothing set | English |

- **User setting:** user menu › *Account settings* › *Preferences* › *Language* (console and
  portal). Saving it also sets the `servio-locale` cookie, so the sign-in page stays in that
  language after sign-out (choosing "Instance default" clears the cookie).
- **Signed-out switch:** the sign-in page has an *English · Deutsch* toggle
  (`setSignedOutLocale` in [`lib/actions/locale.ts`](../lib/actions/locale.ts)) that sets the
  same cookie.
- **Instance default:** *Settings › General › Default language* (AppSetting `APP_LOCALE`), which
  falls back to the `APP_LOCALE` environment variable, then to English. See
  [configuration.md](./configuration.md).
- The root layout ([`app/layout.tsx`](../app/layout.tsx)) sets `<html lang>` and renders
  `<I18nProvider locale>` so client components get the same locale.

## ✍️ Adding or changing UI text

1. Pick the namespace of the module you are working in (`messages/en/tickets.ts` for the Tickets
   module, `common` only for truly generic words like *Save* / *Cancel*).
2. Add the key to the English file **and** the German file. Keys are flat camelCase strings
   within the namespace; dots are allowed for grouping (`"filter.status"`).
3. Use it:

```tsx
// Server Component / Server Action / Route Handler
import { getT } from "@/lib/i18n/server";
const t = await getT("tickets");
return <PageHeader title={t("title")} description={t("description")} />;

// Client Component
"use client";
import { useT } from "@/lib/i18n/client";
const t = useT("tickets");
<Button>{t("newTicket")}</Button>
```

4. Run `pnpm typecheck` and `pnpm test` — `tests/unit/i18n-catalogs.test.ts` fails on a missing,
   empty or extra key and on a placeholder mismatch between the locales.

**Page titles:** replace `export const metadata = { title: "…" }` with

```ts
export async function generateMetadata(): Promise<Metadata> {
  const t = await getT("tickets");
  return { title: t("title") };
}
```

### Message syntax

| Syntax | Example |
| --- | --- |
| Placeholder | `"Assigned to {name}"` → `t("assignedTo", { name })` |
| Plural (`#` = the number) | `"{count, plural, =0 {No tickets} one {# ticket} other {# tickets}}"` |
| Select | `"{kind, select, change {Change} other {Ticket}}"` |
| Rich text | `"Read <link>the guide</link>"` → `t.rich("readGuide", { link: (c) => <Link href="…">{c}</Link> })` |

Placeholders can take React nodes in `t.rich` (`{ name: <strong>{n}</strong> }`). A missing variable
renders empty; a key computed at runtime goes through `t.dyn(key, vars, fallback)`, which falls back
instead of failing type-checking. A key missing in German renders English; a key missing everywhere
renders a humanized form of the key — never the raw key.

### Enum labels (`*_META`)

`lib/constants.ts` keeps the English labels — existing `META.label` reads keep working and stay
English. Translate at render time:

```ts
const te = await getEnumT();           // or useEnumT() in a client component
te(TICKET_STATUS_META[ticket.status]);  // a meta object
te(TICKET_STATUS_META, ticket.status);  // map + value (handles unknown values and null → "—")
te.options(PRIORITY_META);              // [{ value, label }] for a ComboField / filter
```

`ToneBadge` and `StatusBadge` translate registered metas on their own. **Adding a `*_META` map?**
Register it in `ENUM_MAPS` ([`lib/i18n/enums.ts`](../lib/i18n/enums.ts)) and add its labels to
[`messages/de/enums.ts`](../messages/de/enums.ts) — the catalog test lists unregistered maps and
missing labels.

### Server messages

Server Actions return English `error` strings and Zod `fieldErrors`. Translate them where they are
shown, and add the English text to the matching `messages/server/de/<area>.ts`:

```tsx
const tm = useServerMessage();
toast.error(tm(res.error));
<p className="text-destructive">{tm(state.error)}</p>
const fe = tm.fields(state?.fieldErrors) ?? {};
```

Unknown text passes through unchanged (English). Zod's default messages ("Too small: expected
string to have >=3 characters") and messages with numbers or names in them ("Ticket hierarchies
can be at most 3 levels deep.") are covered by regex rules in `messages/server/de/patterns.ts`.
New actions may also translate at the source with `const t = await getT("…")`.

**Cached data stays locale-neutral.** Anything shared across viewers through `unstable_cache`
(e.g. dashboard widget data) must not contain translated text: return raw values or keys and
translate in the component that renders them.

### Emails

The built-in ticket email templates exist per language (`DEFAULT_TEMPLATES_BY_LOCALE` in
[`lib/email-templates.ts`](../lib/email-templates.ts), German in
[`messages/emails/de.ts`](../messages/emails/de.ts)). `mailBrand(recipient)` in
[`lib/mail.ts`](../lib/mail.ts) picks the recipient's language — their `User.locale`, else the
instance default — and `renderTicketEmail` uses that language's default unless an admin has
overridden the template in *Settings › Email templates*; an override is sent as written to every
recipient. Pass the recipient when sending: `await mailBrand(ticket.requester)`.

### Dates and numbers

Never hard-code an English pattern like `format(d, "MMM d, yyyy")`. Use the formatter:

```ts
const f = await getFormatter();   // or useFormatter()
f.date(d);              // Nov 8, 2026 · 8. Nov. 2026
f.date(d, "dateTime");  // Nov 8, 2026, 2:05 PM · 8. Nov. 2026 14:05
f.relative(d);          // 3 minutes ago · vor 3 Minuten
f.number(1234.5);       // 1,234.5 · 1.234,5
```

`<LocalTime render={timeAgo}>` passes the viewer's formatter to its `render` callback.

### Shared components used by Server and Client Components

A component without `"use client"` that renders in both worlds can use neither `getT` nor `useT`.
Either take the text as a prop, or render `<Msg ns="components" k="…" />` (a tiny client
component) for the string.

## 🗣️ German style guide

- Neutral UI German: infinitives and nouns for buttons and labels (*Speichern*, *Ticket anlegen*,
  *Neuer Change*); formal *Sie* only where a sentence addresses the user.
- ITSM loanwords stay: *Ticket*, *Change*, *Problem*, *Asset*, *Release*, *Service*, *SLA*,
  *Dashboard*. Use *Störung* (incident type), *Serviceanfrage* (request type), *Genehmigung*,
  *Wartungsfenster*, *Einstellungen*, *Wissensdatenbank*, *Rufbereitschaft*, *Anfragender*,
  *Bearbeiter*.
- Typography: „deutsche Anführungszeichen“, `…` for ellipses, `–` for ranges, non-breaking
  `z. B.`.

## ➕ Adding a locale

1. Add the code to `LOCALES`, `LOCALE_NAMES` and `INTL_LOCALE` in `lib/i18n/config.ts`, and its
   date-fns locale to `DATE_FNS_LOCALES` in `lib/i18n/format.ts`.
2. Create `messages/<code>/` (copy `messages/de/`) and register it in `messages/index.ts`
   (`catalogs`, `enumCatalogs`, `serverCatalogs`).
3. `pnpm test` lists every key still missing.

## 🚧 Not translated (yet)

- **Sable's prompts and replies** — the AI answers in the language it is addressed in; its system
  prompts stay English.
- **Stored text** — notifications, audit summaries, history entries and system comments are
  written once in English when the event happens.
- **Admin overrides of email templates** — sent as written; only the built-in defaults are
  per language. Code-generated mail text outside the templates (e.g. forwards) stays English;
  `getTForUser()` is there for it.
- **Server messages with free-form names** — e.g. freeze-window verdicts, connector test results
  ("Parsed N rows") and some release readiness errors stay English until a pattern is added.
- **The REST API** — error messages and field names stay English for API clients.
- **Library output asserted by tests** (`lib/*-rules.ts`) stays English; the UI rebuilds the
  same sentences from the same decision in the viewer's language. Example: change self-approval
  (`lib/approval-rules.ts`) returns English refusals, which reach the user through
  `messages/server/de/changes.ts`, while the note above the decision controls is chosen in the
  component from the decision `selfDecisionSettlesBoard(mode)` (`approvalActions.selfApprovalHint`
  / `approvalActions.selfApprovalHintSettles`).
